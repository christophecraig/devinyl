# ADR-0002: Cloudflare Workers + D1 instead of Hetzner VPS + Docker + Litestream

**Status:** Accepted
**Date:** 2026-08-03
**Owner task:** implementation-plan.md 0.6
**Supersedes (for V1):** technical-spec.md §1 "Hosting" row, §15 "Infrastructure & operations" (Hetzner/Caddy/Docker Compose/Litestream shape). The VPS design is **not deleted** — it remains the documented escape hatch (see below) and technical-spec.md is only annotated with pointers to this ADR, not rewritten.

---

## Context

technical-spec.md v1.1 (§1, §15) designs V1 around a **Hetzner VPS** (~6 €/mo): one Node process, `better-sqlite3` + WAL, Litestream continuous replication to object storage, Docker Compose (`caddy` + `app` + `litestream` + self-hosted `plausible`), SSH-based GitHub Actions deploy, in-process `setInterval` jobs, and in-process WebSocket rooms for the V2/V3 real-time forward plan.

The actual starting conditions for this build are: a **$0 budget** (not ~6 €/mo — genuinely zero, no card on file for a POC that may go nowhere), **no Mac** (relevant later for Tauri/iOS, not this ADR, but part of why "keep costs and infra at zero until the product is proven" is the operating principle), **no existing servers or ops experience to lean on**, and a concrete near-term goal: get a working build in front of friends to validate the game loop before spending money or ops effort on anything. Standing up and hardening a VPS (SSH keys, ufw, unattended-upgrades, Docker Compose, Litestream restore drills) is real work and real risk surface for a product that doesn't yet have a single player.

Cloudflare's free tier reaches the same functional shape technical-spec.md wants (one deployable, one SQLite-dialect database, zero-ops backups, no monorepo) at $0, with the CI/CD and preview-URL story built in rather than hand-rolled over SSH. This ADR records that substitution as a deliberate, bounded deviation — not a rewrite of the target architecture, which stays available as the scale-up path.

---

## Decision

Adopt **Cloudflare Workers (compute) + D1 (SQLite-dialect database)** for V1, in place of the Hetzner/Docker/Litestream shape, with the following deviations from technical-spec v1.1. (Reproduced from implementation-plan.md's deviation table, with rationale expanded.)

**Not in the plan's original table but worth naming explicitly for completeness:** the spec's single-node WebSocket design (§14) assumed one Node process could hold all real-time state in memory; Workers/D1 has **no shared process memory across requests or isolates at all**, which is a broader consequence than just WebSocket rooms — see Consequences below.

### Free-tier budget (sanity-checked against the deviation table)

- **Workers:** 100,000 requests/day, **10 ms CPU time per request** (free tier ceiling — this is wall-less CPU time, not wall-clock, but still a hard cap that OG rendering (row 8) and any heavier per-request work must be measured against).
- **D1:** 5,000,000 row reads/day, 100,000 row writes/day, 5 GB storage per database.

These are orders of magnitude above what a friends-POC needs (implementation-plan.md's own sanity check, restated here for the ADR record). The free `*.workers.dev` domain means **D-1 (domain/trademark check) blocks public launch only, not the POC** — the POC can run and be tested with friends before that decision is even made.

## Consequences

### What this buys

- **$0 to reach a testable build**, with CI/CD, preview URLs, and rollback included rather than hand-built.
- **No ops surface to hand-roll or harden** before the product has a single real player: no SSH keys, no `ufw` rules, no unattended-upgrades cadence, no Docker Compose drift, no Litestream sidecar to configure and forget.
- **The schema and query code are not a sunk cost specific to Cloudflare.** Because Drizzle is the abstraction boundary (row 1), the `src/lib/game/`, `src/lib/server/db`, and migration SQL written against D1's SQLite dialect are the same artifacts that would run against `better-sqlite3` on a VPS — see Escape hatch.

### What it constrains, and what has to be re-specified because of it

- **The 10 ms CPU cap is a real constraint, not a formality**, and it bites specifically on plan row 8 (satori OG image rendering) and potentially on any future per-request work that does real computation (audio processing must stay client-side by design already; server-side scoring/finalize logic in §7.3 is comparison/arithmetic over small guessLog arrays and should be cheap, but this should be watched, not assumed, as finalize logic grows). Plan 4.10 makes the satori decision conditional on measured numbers rather than assuming it fits.
- **Loss of in-process shared memory is the deepest architectural consequence**, and it's broader than the deviation table's line items suggest. technical-spec §5.2 designs the Deezer request queue as "a small in-process queue that enforces the [rate] limit" and §10 implies rate-limit token buckets living in server memory. Neither survives Workers' model: **each request may run in a fresh or different isolate, with no memory shared between them.** This is flagged explicitly in implementation-plan §G item 10 and must be re-specified, not assumed away:
  - The **rate-limit token buckets** (search 30/min, session-create 10/min, finalize 20/min per plan 1.18) need a shared counter that survives across isolates — D1 row-based counters (with the write-budget cost that implies against the 100k writes/day D1 ceiling) or Cloudflare's Cache API / KV for a best-effort, eventually-consistent bucket are the two realistic shapes; plan 1.18 commits to "D1/cache" without yet picking one — that choice should be made and tested against real request volume in Phase 1, not deferred indefinitely.
  - The **Deezer request queue** (enforcing whatever the real per-IP/per-app rate limit turns out to be — see ADR-0001 Q2 on how unverified that number is) similarly can't live in a module-level variable. It needs the same D1/cache-backed coordination, or — more robustly — needs to lean on _reacting to_ Deezer's actual 429/`Retry-After` responses per request rather than trying to pre-emptively enforce a shared global counter across isolates, which is architecturally awkward on Workers. This is worth resolving with an actual concurrency test once Phase 1 lands (1.9), not just a design doc.
- **D1's write budget (100k writes/day free)** is generous for gameplay traffic but is exactly the kind of resource that a naive "write a rate-limit counter row on every request" design could burn through unnecessarily — reinforces the point above that the rate-limit mechanism needs a deliberate, tested design, not the first thing that compiles.
- **No self-hosted Plausible** means MET-3 (product analytics) leans entirely on the `metrics_daily` job design that was already in the spec — this ADR doesn't add new risk here, it just confirms the spec's existing "derived from tables that already exist" approach is now load-bearing rather than supplementary.

## Escape hatch

**What it costs to go back to the spec's VPS shape:**

1. **Database:** swap Drizzle's D1 driver for its `better-sqlite3` driver. Same schema files, same migration SQL (D1 and `better-sqlite3` are both SQLite; the plan's own deviation-table entry for row 1 states this explicitly: "Same SQL dialect, same schema; Drizzle abstracts the driver"). Export the live D1 database with `wrangler d1 export` (already produced routinely per row 3) and import it into a fresh `better-sqlite3` file.
2. **Compute:** the SvelteKit app itself is not Workers-specific application code as long as `adapter-cloudflare`-only APIs are avoided in `src/lib/` (Web Crypto, Web Audio, standard fetch — all used here — are portable; Workers-only bindings like the D1 binding itself are isolated behind the Drizzle driver swap in step 1). Swap `adapter-cloudflare` for `adapter-node`, stand up the VPS, Caddy, Docker Compose, and Litestream exactly as technical-spec §15 already documents — that text is left intact in the spec for exactly this purpose.
3. **Jobs:** the Cron-Trigger-dispatched `runJobs(kind)` entry point becomes the body of an in-process `setInterval` again — the job functions themselves don't change (row 2 was designed this way on purpose).
4. **Email:** Resend's HTTP API keeps working from a VPS too (nothing forces the SMTP relay to come back); this migration direction doesn't actually require touching row 4 at all unless cost becomes the driver.
5. **Rate limiting / Deezer queue:** whatever D1/cache-backed design Phase 1 lands on (see Consequences above) either keeps working against a VPS's `better-sqlite3` file, or — if it turns out the escape hatch is taken specifically _because_ the distributed-counter design is fighting the product — reverts to the simpler in-process queue/`Map` the spec originally assumed, which is strictly easier on a single Node process.

**Trigger for actually doing this:** not "Cloudflare is annoying" — the free-tier ceilings (100k req/day Workers, 5M reads/100k writes/day D1) are so far above a friends-POC or even an early public launch that hitting them is itself a good problem. The documented trigger (implementation-plan.md 4.14) is **real launch traffic numbers** reviewed against free-tier usage, weighed against the two paid options: **Cloudflare Workers Paid ($5/mo, lifts the 10ms CPU cap and raises D1/Workers limits)** or **the spec's original Hetzner VPS shape** if D1/Workers' request-scoped model turns out to fight the product's needs badly enough (e.g., the rate-limit/queue re-specification above proves genuinely awkward at scale, or V2/V3's Durable Objects real-time model turns out to cost more than a single Node process with in-memory rooms would). That decision is explicitly deferred until those numbers exist (plan 4.14) — this ADR doesn't pre-decide it, it just keeps both paths open and cheap to take.

## Addendum (2026-08-07): plan 4.10 resolved — dynamic OG images stay deferred

Task 4.10 made the satori decision conditional on measured CPU numbers. They now exist: a representative Devinyl share card (1200×630, three text lines, one bold TTF) rendered through the exact pipeline 4.10 proposed measures **~54 ms CPU per card — satori (JSX→SVG) ~9 ms, resvg (SVG→PNG) ~45 ms** — averaged over 10 warm renders (font parse and module init excluded) on a desktop-class x86 CPU, i.e. a _favourable_ environment: the measurement used `@resvg/resvg-js` (native), while Workers would run `@resvg/resvg-wasm`, which is slower, on shared-tenant CPU.

That is **5× over the free tier's 10 ms cap**, and the cap applies to _every_ Worker invocation — including the "pre-render at creation time into R2/KV" variant, whose rendering still happens inside a Worker request (creation, cron, or queue consumer are all capped the same on the free tier). There is no free-tier invocation context in which this pipeline fits.

**Decision:** keep the static branded OG image + dynamic `og:title`/`og:description` text (row 8's POC posture) as the V1-launch posture too. SHARE-4 remains honored. Revisit only alongside the already-scheduled Workers-Paid decision (plan 4.14 / "Revisit when" below): the $5/mo plan's 30 s CPU limit fits ~54 ms trivially, at which point pre-rendering at creation time into KV/R2 is the right shape.

## Revisit when

- **Free-tier limits are approached** (D1 reads/writes, Workers requests/day, or the 10 ms CPU cap becomes a recurring source of failed requests rather than a satori-specific edge case).
- **V2/V3 real-time work starts** — confirm Durable Objects (row 9) still looks like the right primitive once actual WebSocket-room requirements are specified, rather than assuming this ADR's placeholder choice is final.
- **Monetization or paid infrastructure enters scope** — changes the cost-benefit of the free tier entirely and reopens the VPS-vs-Workers-Paid choice on its merits rather than on "keep it at $0."
- **The rate-limit/Deezer-queue re-specification (Consequences, above) is actually implemented in Phase 1 (plan 1.9, 1.18)** — this ADR describes the constraint and the realistic shapes for solving it, but the concrete design should be recorded (here, as an amendment, or in a follow-up ADR) once it's built and tested, not left as this document's best guess.
- **Plan 4.14's launch-traffic review happens** — this is the explicit, already-scheduled checkpoint where the VPS-vs-Workers-Paid decision gets made with real numbers.
